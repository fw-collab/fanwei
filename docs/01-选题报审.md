## 1. 一句话定位

**做一套 Kotlin 原生、离线优先的单词记忆 App：主 App 完成“背—练—测—复盘”闭环，伴生端以独立 APK 只读展示学习数据看板。**

## 2. 选题说明

- **目标用户：** 需要准备英语考试、希望按计划背单词并看到学习效果的学生。
- **核心问题：** 单词 App 常见问题是“只会打卡，不会复习”；学习记录分散，难以判断哪些词真正掌握、每天该复习什么。
- **解决思路：** 主 App 用简化 SM-2 间隔重复组织复习，用测验和错词本暴露薄弱点；伴生端把学习量、趋势、掌握度和难词集中可视化。
- **范围边界：** 单机离线，不做账号、云同步、社交和 AI 生成；不引入任何跨平台框架。

### 3.1 对照口径

| 编号 | 最低复杂度标准 |

| S5 | 统计与可视化：使用聚合查询生成统计结果，并用图表或统计视图展示 |

### 3.4 核心数据表（支撑 S2）

| 表 | 关键字段 | 关系与索引 |
|---|---|---|
| `WordBook` | `id`、`name`、`description`、`createdAt` | 主键 `id` |
| `Word` | `id`、`bookId`、`spelling`、`phonetic`、`meaning`、`example`、`status`、`wrongCount`、`createdAt` | `bookId` 外键 → `WordBook.id`；`(bookId, spelling)`、`wrongCount` 索引 |
| `StudyRecord` | `id`、`wordId`、`action`、`result`、`createdAt` | `wordId` 外键 → `Word.id`；`createdAt`、`wordId` 索引 |
| `ReviewPlan` | `id`、`wordId`、`nextReviewAt`、`intervalDays`、`ease`、`reviewCount` | `wordId` 唯一外键；`nextReviewAt` 索引 |

数据库 v1 建四表；v2 为 `Word` 增加 `tags` 字段并完成迁移，作为“至少一次版本升级”的验收证据。学习统计不额外建汇总表，直接从 `StudyRecord` 聚合，避免双写不一致。

## 4. 拟用技术点

| 技术点 | 用途 | 难度 | 说明 |
|---|---|---|---|
| Kotlin + Coroutines + Flow | 全项目语言与异步数据流 | 中 | 避免回调地狱，DAO 返回 Flow |
| MVVM + Repository | UI、状态、数据访问分层 | 中 | ViewModel 暴露 StateFlow，页面只渲染状态 |
| Room + KSP | 词书、单词、学习记录、复习计划持久化 | 中 | 含外键、索引、聚合查询和迁移 |
| XML + ViewBinding + Material 3 | 页面与组件 | 低 | 不使用 Compose，降低课程环境差异 |
| RecyclerView + ListAdapter | 单词、错词、难词列表 | 低 | DiffUtil 做局部刷新 |
| Navigation / 显式 Intent | 页面跳转与参数传递 | 低 | 主 App 内部导航；伴生端独立 Activity |
| TextToSpeech | 单词发音 | 低 | 系统能力，无需网络 |
| 自定义 View（ProgressRingView） | 今日完成度进度环 | 中 | Canvas 绘制，减少对第三方图表的依赖 |
| 属性动画 | 卡片翻转、列表切换 | 中 | 提升交互完整度 |
| ContentProvider + ContentResolver | 主 App 向伴生端只读共享 Room 数据 | 高 | 本项目关键难点，使用 signature 权限 |
| MPAndroidChart | 折线图、饼图、条形图 | 低 | JitPack 依赖，需配置仓库 |
| DataStore Preferences | 每日目标、TTS 开关、主题 | 低 | 替代直接使用 SharedPreferences |
| JUnit4 + AndroidX Test + Espresso | 单元测试与 UI 测试 | 中 | Room 使用内存数据库；Provider 做查询测试 |
| Git + `.gitignore` | 版本管理与提交规范 | 低 | 忽略构建产物、IDE 配置和签名文件 |

**明确不使用的技术：** Flutter、React Native、uni-app、Compose Multiplatform、WebView 套壳；全部界面与逻辑使用 Kotlin + Android SDK 原生实现。

## 5. 硬性约束响应

| 约束 | 响应方式 |
|---|---|
| 伴生模块独立可启动 | `:data_board_module` 是 Android Library，本身不可安装；增加 `:board_app` 作为独立 APK 宿主，拥有独立 `applicationId`、Launcher 和桌面图标，页面与业务逻辑仍放在 Library |
| 读取主 App Room 数据库 | 主 App 内 Room 为唯一数据源，通过只读 `WordBoardProvider` 暴露查询 URI；伴生端用 `ContentResolver` 读取，不直接打开数据库文件、不建副本 |
| 禁止跨平台框架 | 全 Kotlin 原生；不使用任何跨平台 UI/运行时；不引入 WebView 承载业务页面 |
| 数据安全 | Provider 仅支持 `query`，不实现写操作；自定义 `signature` 读权限；主 App 与伴生端使用同一签名证书 |

> 直接让另一个 APK 打开 `/data/data/.../word_memory.db` 在 Android 沙箱下不可行；`sharedUserId` 已弃用且不安全。Provider 方案是在“读取主 App Room 数据”这一需求下可落地、可演示、可解释的工程做法。

**依赖方向：** `:board_app` → `:data_board_module`；`:app` 保持独立，不依赖看板 Library，避免主 App 被伴生端 UI 与图表库耦合。

## 6. 项目亮点

1. **双端但单一数据源：** 主 App 写入、伴生端只读，避免两份数据不一致。
2. **学习闭环而不是单词列表：** 学习结果进入复习计划，错词进入错词本，测验成绩进入统计。
3. **数据可视化有明确用途：** 趋势看节奏，掌握度看结构，难词榜看薄弱点。
4. **工程化边界清楚：** Library 承载看板复用，薄宿主负责独立启动，权限与签名边界可验收。

## 7. 可行性与风险应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Provider 权限/签名配置错误 | 伴生端查询被拒 | 调试版共用默认 debug 签名；发布版显式配置同一 `signingConfig`；捕获 `SecurityException` 并给出提示 |
| 主 App 未安装或未建库 | 看板无数据 | 捕获 `IllegalArgumentException`/空游标，展示“请先安装并打开主 App”空态 |
| 图表库 JitPack 拉取失败 | 构建失败 | 配置 JitPack；必要时改用自绘 View 或本地依赖 |
| 功能范围偏大 | 进度风险 | 优先完成 B4-01～B4-04 与 P2-01～P2-03；P2-05 等作为可裁剪项，但保留最低复杂度证据 |
| Room 聚合查询性能 | 数据量大时卡顿 | 为日期、单词外键、错误次数建索引；查询放到 IO 线程；看板只查聚合结果 |
